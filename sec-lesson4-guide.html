تصميم التوثيق ومفاهيم كلمة المرور

Authentication Design & Password Concepts

أي آلية توثيق يجب أن تخدم CIA الثلاثة معًا

Any authentication mechanism must serve all three CIA properties

تصميم التوثيق الجيد يحقّق:

Good authentication design achieves:

  • السرية: يحافظ على سرية بيانات الاعتماد.
  • السلامة: لا يستطيع المهاجم تجاوز أو تخريب آلية التوثيق.
  • التوفر: لا يسبّب تأخيرًا غير مبرَّر أو مشاكل دعم فني.
  • Confidentiality: keeps credentials secure.
  • Integrity: threat actors cannot bypass or subvert the mechanism.
  • Availability: the mechanism does not cause undue delay or support issues.

أبسط عامل توثيق: Something you know (عامل المعرفة) — كلمة المرور أو رقم التعريف الشخصي (PIN).

The simplest authentication factor: something you know — a password or PIN.

مفاهيم كلمة المرور

Password Concepts

  • الطول (Length) والتعقيد (Complexity): مزيج من أنواع الأحرف — رغم أن إرشادات NIST الحديثة تُقلّل التركيز على التعقيد المُفرَط لصالح الطول وعدم إعادة الاستخدام.
  • التقادم (Aging) وإعادة الاستخدام والسجل (Reuse/History) والانتهاء (Expiration): سياسات تقليدية لا تزال مطلوبة بمعايير الاختبار، لكن NIST الحديثة تنصح بعدم فرض تغيير دوري إجباري بدون سبب (لأنه يُشجّع أنماطًا يسهل تخمينها).
  • تلميحات كلمة المرور (Password Hints): خطر أمني إن كانت سهلة التخمين أو الهندسة الاجتماعية.
  • Length and Complexity: a mix of character types — though updated NIST guidance reduces emphasis on excessive complexity in favor of length and non-reuse.
  • Aging, Reuse/History, and Expiration: traditional policies still expected on the exam, but modern NIST guidance advises against forced periodic changes without cause (since it encourages easily-guessed patterns).
  • Password hints: a security risk if easily guessed or socially engineered.

ملايين كلمات المرور المُسرَّبة من اختراقات سابقة (هاشات و/أو نصوص صريحة مع أسماء مستخدمين أو بريد إلكتروني) تُغذّي هجمات password spraying — تجربة كلمة مرور شائعة واحدة على عدد كبير من الحسابات لتفادي إغلاق الحساب.

Millions of passwords leaked from past breaches (hashes and/or plaintext, plus usernames or emails) feed password spraying attacks — trying one common password across many accounts to avoid account lockout.

مديرو كلمات المرور

Password Managers

خزنة (vault) مشفَّرة تُفتح بكلمة مرور رئيسية واحدة (master password) — مدمجة في نظام التشغيل/المتصفح، أو تطبيقات سحابية/إضافات من طرف ثالث. تُتيح توليد كلمات مرور عشوائية طويلة لكل موقع وتعبئتها بأمان — أطول وأصعب تخمينًا مما يقدر عليه معظم المستخدمين ذهنيًا، لكن التطبيقات نفسها ليست خالية من ثغرات محتملة.

An encrypted vault unlocked by a single master password — built into the OS/browser, or a third-party cloud/plug-in app. Enables per-site random password generation and secure filling — longer and harder to guess than most users could remember on their own, though the apps themselves aren't free of vulnerabilities.

سؤال شائع: "ما توصية NIST الحديثة بشأن كلمات المرور؟" ← التركيز على الطول وعدم إعادة الاستخدام، مع تقليل الاعتماد على التعقيد المُفرَط والتغيير الدوري الإجباري دون سبب. لكن معايير الاختبار نفسها لا تزال تعتبر Complexity وAging سياسات مقبولة — احفظي الاثنين معًا.
Common question: "What's NIST's modern recommendation on passwords?" ← focus on length and avoiding reuse, with reduced emphasis on excessive complexity and forced periodic changes without cause. But the exam objectives themselves still treat complexity and aging as acceptable policies — know both.

Multifactor Authentication & Tokens

عاملان مختلفان النوع، لا نفس النوع مكرَّرًا

Two different factor types, not the same type repeated

MFA (Multifactor Authentication): تجمع بين شيء تعرفينه وشيء تملكينه — وليس شيئين تعرفينهما (سؤالان أمنيان مثلًا لا يُعتبران MFA حقيقيًا).

MFA: combines something you KNOW and something you HAVE — NOT something you know and something else you know (two security questions is not true MFA).

التوثيق الحيوي — Biometric

Biometric Authentication

مراحله: Enrollment (تسجيل أولي) ← استشعار واستخراج ميزات (sensor and feature extraction). مقاييس الفعالية:

Stages: Enrollment ← sensor and feature extraction. Efficacy metrics:

  • False Rejection Rate (FRR) / Type I error: رفض شخص مصرَّح له خطأً.
  • False Acceptance Rate (FAR) / Type II error: قبول شخص غير مصرَّح له خطأً — عادةً الأخطر أمنيًا.
  • False Rejection Rate (FRR) / Type I error: wrongly rejecting an authorized person.
  • False Acceptance Rate (FAR) / Type II error: wrongly accepting an unauthorized person — usually the more security-critical error.

عوامل أخرى للمقارنة: سرعة الإنجاز (throughput)، التكلفة، وإمكانية الوصول (inaccessibility) لبعض المستخدمين. أمثلة: التعرف على بصمة الإصبع والتعرف على الوجه. ملاحظة إضافية: CAPTCHA تتحقق من أن الطلب صادر من إنسان فعلي وليس بوت.

Other comparison factors: throughput, cost, and inaccessibility for some users. Examples: fingerprint recognition and facial recognition. Side note: CAPTCHA verifies a request is coming from an actual human, not a bot.

الرموز العتادية

Hard Authentication Tokens

أنواع توليد الرمز: قائم على الشهادات (يحتاج PKI)، كلمة مرور لمرة واحدة (OTP)، أو FIDO U2F. أشكاله: بطاقة ذكية، fob لـOTP، أو مفتاح أمان (security key) — غالبًا يتطلب تفعيل يدوي يُثبت الحضور الفعلي.

Token generation types: certificate-based (requires PKI), one-time password (OTP), or FIDO U2F. Form factors: smart card, OTP fob, or a security key — often needing an activation gesture that proves physical presence.

الرموز البرمجية

Soft Authentication Tokens

يُرسَل رمز عبر قناة خارج النطاق (out-of-band): رسالة نصية SMS، بريد إلكتروني، مكالمة صوتية، إشعار دفع (push notification)، أو تطبيق مصادقة (authenticator app) — مع احتمال اعتراض الرمز أثناء النقل (خصوصًا SMS).

A code is transmitted via an out-of-band channel: SMS, email, phone call, push notification, or an authenticator app — with the possibility of interception during transit (especially SMS).

التوثيق بلا كلمة مرور — Passwordless

Passwordless Authentication

يعتمد على المُوثِّق (authenticator) فقط بدل كلمة المرور. الحسابات تُعرَّف بزوج مفاتيح عام/خاص (دون الحاجة لـPKI كاملة بالضرورة)، والمفتاح الخاص يبقى محفوظًا فقط داخل الموثِّق نفسه. قد يطلب الموثِّق بصمة أو PIN محليًا كإثبات حضور (local gesture).

Relies on the authenticator alone instead of a password. Accounts are identified by a public/private key pair (not necessarily requiring full PKI), and the private key is stored only on the authenticator. The authenticator may require a biometric or PIN locally as a proof-of-presence (local gesture).

Attestation: عملية إثبات أن الموثِّق نفسه هو جذر ثقة (root of trust) موثوق — لا تخلطيها بـAuthentication (التي تثبت هوية المستخدم).

Attestation: the process of proving the authenticator itself is a trustworthy root of trust — don't confuse it with Authentication (which proves the user's identity).

الفرق الجوهري: MFA لا تزال تحتفظ بكلمة مرور + عامل إضافي، بينما Passwordless يعتمد على الموثِّق وحده بلا كلمة مرور من الأساس. FRR/FAR سؤال كلاسيكي: تذكّري FAR = قبول غير مصرَّح (الأخطر)، FRR = رفض مصرَّح له (إزعاج فقط).
The key distinction: MFA still retains a password plus an additional factor, while Passwordless relies on the authenticator alone with no password at all. FRR/FAR is a classic question: remember FAR = accepting the unauthorized (more security-critical), FRR = rejecting the authorized (just an inconvenience).

Access Control Models

من يقرر مَن يصل إلى ماذا؟

Who decides who gets access to what?

The key difference between DAC and MAC: in DAC, decision-making lies with the resource owner; in MAC, it lies with the system owner (controls are enforced system-wide and cannot be countermanded by users "within" the system).

مجموعات الأمان مقابل الأدوار

Security Groups vs. Roles

تُعيَّن الصلاحيات لمجموعات أمان (security groups)، وتُضاف حسابات المستخدمين للمجموعة المناسبة — يمكن ربط المجموعات بالأدوار، لكنها ليست مطابقة تمامًا: توجد أيضًا أنظمة صلاحيات قائمة على الأدوار صراحةً (مثل أنظمة IAM في Azure أو AWS).

Permissions are assigned to security groups, and user accounts are added to the relevant group — groups can map to roles, but they're not identical: there are also explicitly role-based permission systems (like Azure or AWS IAM).

ضبط الوصول القائم على القواعد

Rule-Based Access Control

غير تقديري (non-discretionary) — النظام هو من يحدد القواعد، لا المستخدمون. تندرج تحته MAC وRBAC وABAC، بالإضافة إلى مفاهيم مثل Conditional Access وContinual Authentication، وأدوات نظامية مثل User Account Control (UAC) على ويندوز وsudo على لينكس. ملاحظة: القاعدة قد لا ترتبط أصلًا بهوية المستخدم (مثل قاعدة ACL على جدار حماية).

Non-discretionary — the system determines the rules, not users. This umbrella includes MAC, RBAC, and ABAC, plus concepts like Conditional Access and Continual Authentication, and system tools like User Account Control (UAC) on Windows and sudo on Linux. Note: a rule doesn't necessarily depend on user identity at all (e.g. a firewall ACL rule).

سؤال كلاسيكي: "موظف يملك ملفًا ويستطيع منح زميله صلاحية قراءته بنفسه" ← DAC. "نظام عسكري يفرض تصنيفات سرية لا يستطيع أي مستخدم تجاوزها" ← MAC. "مستخدم يُمنح صلاحيات تلقائيًا فور تعيينه بوظيفة مُحاسِب" ← RBAC. "الوصول يُسمح فقط إذا كان الوقت ضمن ساعات الدوام ومن جهاز مُدار" ← ABAC.
Classic question: "An employee owns a file and can personally grant a colleague read access" ← DAC. "A military system enforces classification labels no user can override" ← MAC. "A user automatically gets permissions the moment they're assigned the Accountant role" ← RBAC. "Access is only allowed if it's during work hours AND from a managed device" ← ABAC.

إدارة الحسابات، أقل الصلاحيات، والوصول المميّز

Account Management, Least Privilege & Privileged Access

من التزويد بالحساب إلى إلغائه، مرورًا بالحد الأدنى الضروري من الصلاحيات

From account provisioning to deprovisioning, with only the minimum necessary permissions in between

مبدأ أقل الصلاحيات

Least Privilege Permission Assignments

منح الصلاحيات الكافية فقط لأداء المهمة، لا أكثر. التبعات عند الإخلال به:

Granting sufficient permissions only to do the job — no more. Implications when violated:

  • صلاحيات غير كافية: تعطيل العمل وطلبات دعم متكررة.
  • Authorization creep: تراكم صلاحيات زائدة بمرور الوقت (كل ما تغيّر دور الموظف تُضاف صلاحيات جديدة دون سحب القديمة).
  • المراجعة (Auditing): ضرورية لاكتشاف الصلاحيات الزائدة ومعالجتها دوريًا.
  • Insufficient permissions: blocks work and generates repeated support requests.
  • Authorization creep: excess permissions accumulate over time (each role change adds new permissions without removing old ones).
  • Auditing: essential for periodically discovering and remediating excess permissions.

"صلاحيات دائمة" افتراضية لحساب المدير/الجذر (standing permissions) كانت سبب كثير من الاختراقات الأمنية تاريخيًا.

Default "standing" administrator/root permissions have historically been the cause of many security breaches.

تزويد الحسابات وإلغاؤها

Provisioning & Deprovisioning

Provisioning: إثبات الهوية (identity proofing) ← إصدار بيانات الاعتماد ← تخصيص الأصول ← توعية بالسياسات وتدريب أمني ← تعيين الصلاحيات.

Provisioning: identity proofing ← issuing credentials ← asset allocation ← policy awareness/security education ← permission assignments.

Deprovisioning: عند مغادرة موظف/متعاقد أو تغيير دوره — إزالة أو تعطيل الصلاحيات فورًا لتفادي وصول غير مصرَّح.

Deprovisioning: when an employee/contractor leaves or changes roles — remove or disable permission assignments immediately to prevent unauthorized access.

سمات الحساب وسياسات الوصول

Account Attributes & Access Policies

سمات الحساب: معرّف الأمان (SID)، اسم الحساب، بيانات الاعتماد، وسمات ملف تعريف موسَّعة (إعدادات وملفات لكل تطبيق). سياسات الوصول: صلاحيات الملفات، حقوق الوصول، وكائنات سياسة المجموعة (Active Directory GPOs).

Account attributes: Security Identifier (SID), account name, credential, and extended profile attributes (per-app settings and files). Access policies: file permissions, access rights, and Active Directory Group Policy Objects (GPOs).

قيود الحسابات

Account Restrictions

  • سياسات قائمة على الموقع: الموقع الشبكي/المنطقي، الموقع الجغرافي (عبر عنوان IP أو خدمات الموقع).
  • قيود زمنية: ساعات الدخول المسموحة (logon hours)، مدة الجلسة (logon duration)، واكتشاف "سفر مستحيل" أو دخول مريب (impossible travel time / risky login) — تسجيل دخول من دولتين متباعدتين خلال وقت قصير جدًا يستحيل السفر بينهما فعليًا.
  • صلاحيات مؤقتة (Temporary permissions): تُمنح لفترة محدودة ثم تنتهي تلقائيًا.
  • Location-based policies: network/logical location, geolocation (via IP address or location services).
  • Time-based restrictions: logon hours, logon duration, and detecting "impossible travel time"/risky logins — a login from two distant countries within a timeframe too short to physically travel between them.
  • Temporary permissions: granted for a limited time, then automatically expire.

إدارة الوصول المميّز — PAM

Privileged Access Management (PAM)

سياسات وإجراءات وضوابط تقنية لمنع إساءة استخدام الحسابات ذات الصلاحيات النظامية الواسعة — لا يقتصر مفهوم "الحساب المميّز" على مدير/جذر النظام فقط؛ أي صلاحية إدارية قد تؤثر على النموذج الأمني (أو تصل لبيانات حساسة/سرّية) تُعتبر مميّزة، وقد تنطبق على حسابات الخدمات والتطبيقات أيضًا.

Policies, procedures, and technical controls to prevent malicious abuse of accounts with system-wide access — "privileged account" isn't limited to admin/root; any administrative permission that could affect the security model (or access sensitive/private data) counts as privileged, and this can extend to service and application accounts too.

  • محطات عمل إدارية آمنة (secure administrative workstations)
  • سياسة "لا صلاحيات دائمة" (zero standing privileges) للمدراء
  • رفع مؤقت للصلاحية (temporary elevation) عند الحاجة فقط
  • خزن/وساطة كلمات المرور (password vaulting/brokering)
  • بيانات اعتماد لحظية (ephemeral credentials) تنتهي بعد الاستخدام
  • Secure administrative workstations
  • Zero standing privileges policies for administrators
  • Temporary elevation only when needed
  • Password vaulting/brokering
  • Ephemeral credentials that expire after use
مبدأ PAM المحوري: Zero Standing Privileges — بدل أن يملك المدير صلاحيات كاملة طوال الوقت، تُرفَع صلاحياته مؤقتًا فقط عند الحاجة الفعلية ثم تنتهي تلقائيًا. هذا يقلّل النافذة الزمنية التي يستطيع فيها مهاجم استغلال حساب مُخترَق ذي صلاحيات عالية.
The core PAM principle: Zero Standing Privileges — instead of an administrator holding full permissions at all times, privileges are elevated only temporarily when actually needed, then automatically expire. This shrinks the window an attacker has to exploit a compromised high-privilege account.

إدارة الهوية — الدلائل، تسجيل الدخول الموحّد، والاتحاد الفدرالي

Identity Management — Directories, SSO & Federation

كيف تُدار الهويات وتُشارَك الصلاحيات عبر أنظمة متعددة

How identities are managed and authorizations shared across multiple systems

التوثيق المحلي والشبكي والبعيد

Local, Network & Remote Authentication

يجب التفريق بين نطاق تسجيل الدخول: قاعدة بيانات كلمات مرور جهاز محلي واحد، أو دليل شبكي مركزي. على ويندوز: تسجيل دخول محلي، شبكي (عبر Kerberos أو NTLM)، أو بعيد. على لينكس: ملفا /etc/passwd و/etc/shadow، مع وحدات توثيق قابلة للتوصيل (PAMs - Pluggable Authentication Modules).

The scope of a login matters: a single local machine's password database, versus a centralized network directory. On Windows: local sign-in, network sign-in (via Kerberos or NTLM), or remote sign-in. On Linux: the /etc/passwd and /etc/shadow files, plus Pluggable Authentication Modules (PAMs).

خدمات الدليل — Directory Services

Directory Services

قاعدة بيانات مركزية للموضوعات: مستخدمون، أجهزة، مجموعات/أدوار أمنية، وخدمات — بالإضافة لقوائم التحكم بالوصول (التفويضات). المعيار: X.500 وبروتوكول LDAP (Lightweight Directory Access Protocol). تُعرَّف الكائنات بأسماء مميَّزة (Distinguished Names) بصيغة أزواج سمة=قيمة:

A centralized database of subjects: users, computers, security groups/roles, and services — plus access control lists (authorizations). The standard: X.500 and the LDAP (Lightweight Directory Access Protocol). Objects are identified by Distinguished Names as attribute=value pairs:

CN=WIDGETWEB, OU=Marketing, O=Widget, C=UK, DC=widget, DC=foo

الاهتمامات الأمنية الرئيسية بخدمات الدليل: سرية المعلومات (وصول القراءة)، سلامتها (وصول الكتابة)، والتوفر (منع هجمات حجب الخدمة على خادم الدليل).

The main security concerns with directory services: confidentiality of information (read access), integrity (write access), and availability (preventing denial-of-service against the directory server).

تسجيل الدخول الموحّد — SSO عبر Kerberos

Single Sign-on via Kerberos

مكوّنات Kerberos: العملاء (clients)، خوادم التطبيقات (application servers)، ومركز توزيع المفاتيح (KDC - Key Distribution Center) الذي يضم خدمتين:

Kerberos components: clients, application servers, and the KDC (Key Distribution Center), which contains two services:

  • Authentication Service: يصدر Ticket Granting Ticket (TGT) بعد التحقق الأولي من هوية المستخدم.
  • Ticket Granting Service: يستخدم الـTGT لإصدار Service Ticket لكل خدمة يطلبها المستخدم.
  • Authentication Service: issues a Ticket Granting Ticket (TGT) after initial identity verification.
  • Ticket Granting Service: uses the TGT to issue a Service Ticket for each service the user requests.
العميل والخادم لا يعرف أحدهما كلمة مرور الآخر — فقط الـKDC يعرف الاثنين، ويثبت للخادم أن العميل أدخل كلمة المرور الصحيحة
The client and server don't know each other's password — only the KDC knows both, proving to the server that the client entered the correct password

الاتحاد الفدرالي — Federation

Federation

شبكات تحت إدارات مستقلة تشارك هويات المستخدمين فيما بينها. المفاهيم الأساسية: مزوّد الهوية (Identity Provider - IdP) يُصدر ادعاءات (claims)، ومزوّد الخدمة (Service Provider) يثق بها بدل توثيق المستخدم مباشرة بنفسه — عبر أطر عمل وبروتوكولات مشتركة تحقق التوافقية (interoperability).

Networks under separate administrative control share user identities. Core concepts: an Identity Provider (IdP) issues claims, and a Service Provider trusts them instead of authenticating the user itself — via shared frameworks and protocols achieving interoperability.

SAML

Security Assertion Markup Language

معيار مفتوح لتنفيذ التواصل بين مزوّد الهوية ومزوّد الخدمة، عبر ادعاءات/تصديقات (assertions) بصيغة XML مُوقَّعة رقميًا (وفق مواصفة XML Signature)، تُنقَل عادة عبر HTTPS أو SOAP. الفكرة الجوهرية: مزوّد الخدمة لا يُوثِّق المستخدم مباشرة؛ بل يحصل على تصديق من مزوّد الهوية بأن المستخدم تم توثيقه.

An open standard for identity/service provider communication via digitally signed XML assertions (per the XML Signature spec), typically transported over HTTPS or SOAP. The core idea: the service provider doesn't authenticate the user directly; it obtains an assertion from the identity provider that the user has been authenticated.

OAuth

Open Authorization (OAuth)

خدمات اتحاد فدرالي "محورها المستخدم"، أنسب لمواقع المستهلكين، مبنية على واجهات RESTful APIs — هو إطار عمل للتنفيذ لا بروتوكول واحد ثابت. مصمَّم لنقل التفويضات (Authorizations) لا التوثيق الصريح للموضوع. العميل (موقع/تطبيق) يتفاعل مع مزوّد هوية OAuth وخوادم موارد تحمل بيانات المستخدم الأساسي، بمسارات مختلفة (خادم لخادم، أو تطبيق جوال لخادم) — غالبًا باستخدام JWT (JSON Web Token).

"User-centric" federated services better suited to consumer websites, built on RESTful APIs — a framework for implementation, not a single fixed protocol. Designed to communicate Authorizations, not explicitly authenticate a subject. The client (a site/app) interacts with an OAuth IdP and resource servers holding the principal's data, via different flow types (server-to-server, or mobile app-to-server) — often using a JWT (JSON Web Token).

لا تخلطي: SAML يركّز على التوثيق (يثبت "من أنت")، وOAuth يركّز على التفويض (يثبت "ماذا يُسمح لك بفعله" أو للتطبيق الوصول إليه نيابة عنك). وعميل OAuth ليس المستخدم نفسه — بل الموقع أو التطبيق الذي يتفاعل نيابةً عنه مع مزوّد الهوية أو خادم الموارد.
Don't confuse them: SAML centers on authentication (proving "who you are"), while OAuth centers on authorization (proving "what you/the app is allowed to do on your behalf"). And an OAuth client is not the user — it's the site or app interacting with the IdP or resource server on the user's behalf.
